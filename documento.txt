================================================================================
          DOCUMENTO TÉCNICO: ANÁLISIS DE LA SUITE DE PRUEBAS DE ROOTDEV
================================================================================

Este documento detalla el funcionamiento interno, la estructura de clases, y el 
comportamiento a nivel de base de datos y red del conjunto de pruebas del backend 
de RootDev (Django framework).

--------------------------------------------------------------------------------
1. ARQUITECTURA DE PRUEBAS Y FLUJO DE EJECUCIÓN
--------------------------------------------------------------------------------
Las pruebas del backend utilizan el framework de pruebas nativo de Django, el cual 
está construido sobre la librería estándar `unittest` de Python. 

Al ejecutar el comando `python manage.py test freelance_core`:
1. Django crea una base de datos temporal exclusiva para pruebas (por defecto con
   el prefijo `test_`).
2. Ejecuta todas las migraciones para replicar la estructura del modelo relacional 
   (User, Client, Project, Task).
3. Instancia las clases de prueba que heredan de `django.test.TestCase`.
4. Envuelve cada método de prueba individual dentro de una transacción de base 
   de datos. Al finalizar la prueba, realiza un ROLLBACK automático de dicha 
   transacción, asegurando un estado limpio ("hermeticidad") para la siguiente.
5. Destruye la base de datos temporal una vez finalizado el proceso.

--------------------------------------------------------------------------------
2. ESTRUCTURA DE LA CLASE PRINCIPAL: RootDevTests
--------------------------------------------------------------------------------
Ubicación: freelance_core/tests.py
Clase: class RootDevTests(TestCase)

Esta clase contiene la lógica de inicialización y los casos individuales de 
prueba de unidad e integración.

MÉTODO DE CONFIGURACIÓN (Fixtures):
* `setUp(self)`:
  Se ejecuta automáticamente antes de cada método de prueba. Su propósito es 
  preparar el estado básico (fixture) de la base de datos:
  - Crea un usuario de prueba en `django.contrib.auth.models.User` utilizando 
    `User.objects.create_user(username='testuser', password='password123')`.
  - Crea una instancia de `Client` vinculada al usuario creado, con datos de 
    prueba específicos ('Cliente de Prueba', 'cliente@prueba.com', 'Empresa Test').
  Esto permite que cada test empiece con un registro de User y un registro de 
  Client ya persistidos en la base de datos transaccional temporal.

--------------------------------------------------------------------------------
3. ANÁLISIS TÉCNICO DE CADA CASO DE PRUEBA (MÉTODOS)
--------------------------------------------------------------------------------

--------------------------------------------------------------
A. test_client_creation(self)
--------------------------------------------------------------
* Propósito: Validar el modelo Client y sus relaciones directas.
* Funcionamiento:
  - Lee el objeto `self.test_client` creado en el `setUp()`.
  - Evalúa mediante `self.assertEqual` que el campo `name` sea exactamente
    'Cliente de Prueba'.
  - Verifica la relación de clave foránea (`ForeignKey`) comprobando que el 
    username del usuario asociado sea 'testuser'.
  - Realiza un conteo total de la tabla Client en BD (`Client.objects.count()`), 
    asegurándose de que sea exactamente 1.

--------------------------------------------------------------
B. test_project_creation(self)
--------------------------------------------------------------
* Propósito: Validar la creación del modelo Project y su enlace de clave foránea.
* Funcionamiento:
  - Invoca `Project.objects.create` asociando el objeto `self.test_client` 
    como su campo `client`.
  - Configura los campos del proyecto (`name='Proyecto Alpha'`, 
    `description='Descripción del proyecto alpha'`, `status='active'`).
  - Asegura que el proyecto persistido retenga la relación con el cliente 
    (`project.client.name` == 'Cliente de Prueba').
  - Valida que la inserción fue correcta comprobando que `Project.objects.count()` 
    sea igual a 1.

--------------------------------------------------------------
C. test_task_creation(self)
--------------------------------------------------------------
* Propósito: Validar la integridad de los atributos de la clase Task.
* Funcionamiento:
  - Crea un nuevo proyecto intermedio ('Proyecto Beta') para evitar colisiones.
  - Instancia una tarea con `priority='high'` y `status='todo'` asignándola 
    a dicho proyecto.
  - Compara mediante aserciones que los campos `priority` y `project` se 
    hayan configurado correctamente.
  - Valida que `Task.objects.count()` sea 1.

--------------------------------------------------------------
D. test_cascade_deletion(self)
--------------------------------------------------------------
* Propósito: Validar las restricciones de integridad referencial de base de 
  datos (`ON DELETE CASCADE`) configuradas en el modelo relacional.
* Funcionamiento:
  - Estructura una jerarquía de datos temporal: 
    Cliente -> Proyecto ('Proyecto a borrar') -> Tarea ('Tarea a borrar').
  - Llama al método `delete()` sobre la instancia `self.test_client`.
  - Gracias a la propiedad `on_delete=models.CASCADE` definida en los campos 
    `client` de Project y `project` de Task en `models.py`, el motor de la base 
    de datos elimina automáticamente todas las entidades dependientes en cascada.
  - El test valida esto comprobando que el conteo en BD tanto de Project como 
    de Task retorne 0 de forma inmediata.

--------------------------------------------------------------
E. test_login_required_redirect(self)
--------------------------------------------------------------
* Propósito: Comprobar la seguridad del middleware de autenticación de Django 
  y los decoradores `@login_required` aplicados en las vistas.
* Funcionamiento:
  - Utiliza el cliente HTTP simulado integrado de Django (`self.client`).
  - Hace una petición GET a la ruta raíz ('/').
  - Al no haber una sesión iniciada previamente en el cliente, el backend debe 
    bloquear la petición y responder con un código de redirección temporal `302`.
  - Verifica que la respuesta contenga en su cabecera de redirección la ruta 
    del login estándar (`/login/`).

--------------------------------------------------------------
F. test_successful_login(self)
--------------------------------------------------------------
* Propósito: Probar el flujo de inicio de sesión exitoso mediante peticiones POST.
* Funcionamiento:
  - Realiza un POST a la URL de login (`/login/`) enviando el payload con las 
    credenciales válidas creadas durante el `setUp()` (`testuser` / `password123`).
  - Espera un código de estado `302`, lo cual indica redirección tras un login 
    exitoso.
  - Verifica el estado de la sesión de Django inspeccionando `self.client.session`. 
    Busca la presencia del ID interno del usuario bajo la clave `_auth_user_id`.
    Si existe, significa que la sesión del navegador virtual del test quedó 
    correctamente autenticada y vinculada en el Backend.

--------------------------------------------------------------
G. test_user_registration(self)
--------------------------------------------------------------
* Propósito: Validar que el flujo de registro de nuevos usuarios en el sistema 
  sea compatible con el formulario interno de creación.
* Funcionamiento y Detalle Técnico Especial:
  - En la primera parte del test, se intenta hacer un POST con los campos:
    `{'username': 'newuser', 'password': 'newpassword123', 'password_confirm': 'newpassword123'}`.
    Esta petición no crea un usuario, ya que en la vista `register_view` del 
    archivo `views.py` se utiliza la clase nativa `UserCreationForm` de Django.
  - La clase `UserCreationForm` espera estrictamente los campos `password1` 
    (para la contraseña) y `password2` (para la confirmación). Cualquier otro 
    campo causa un fallo en la validación del formulario (`form.is_valid() == False`).
  - Por esta razón, el test realiza una segunda llamada POST con las claves 
    correctas: `{'username': 'realnewuser', 'password1': 'newpassword123', 'password2': 'newpassword123'}`.
  - Finalmente, valida la creación exitosa en la base de datos verificando 
    mediante el ORM si el usuario `realnewuser` existe:
    `User.objects.filter(username='realnewuser').exists()`.

--------------------------------------------------------------------------------
4. COMANDOS DE DIAGNÓSTICO Y EJECUCIÓN
--------------------------------------------------------------------------------

Para correr las pruebas e inspeccionar salidas a nivel técnico:

1. Ejecución estándar:
   $ python manage.py test freelance_core

2. Con nivel de detalle alto (verbosity 2), lo cual lista los nombres de los 
   métodos de prueba ejecutados y su resultado individual:
   $ python manage.py test freelance_core -v 2

3. Evitando destruir la base de datos de pruebas (útil para inspeccionar el estado
   de las tablas tras fallos si se utiliza en conjunto con flags de debug):
   $ python manage.py test freelance_core --keepdb
